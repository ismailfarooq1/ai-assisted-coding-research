Understanding the research: What exactly are you trying to prove?
Your research would investigate one fundamental question:

Can a structured development environment help AI coding agents build and maintain large software projects more reliably, efficiently, and consistently than conventional development environments?

You're not simply trying to create a folder structure. You're trying to demonstrate, through controlled experiments, whether your proposed structure actually improves AI-assisted software engineering.

Let's break down what that means in practice.
1. What does the research actually consist of?
Think of your research as five stages.
1. Identify problems
What goes wrong when AI works on large codebases?
2. Study existing solutions
What have researchers and existing tools already tried?
3. Propose a solution
Design your own structured development environment
4. Run controlled experiments
Compare AI performance with and without your structure
5. Analyze and publish
What improved, what didn't, and why?

The research is successful if you can produce a credible, reproducible answer to these questions, even if some of your hypotheses turn out to be wrong.

A positive result would support the usefulness of your framework. A negative result could show which proposed components are unnecessary or counterproductive.
2. Your four main research questions
I would begin with four research questions rather than investigating every possible problem with AI-assisted coding.
Research question	What you're investigating
RQ1: Memory	Does persistent structured project knowledge help AI continue development after its conversational context is reset?
RQ2: Architecture	Does explicit architectural knowledge reduce errors and violations of software design constraints?
RQ3: Efficiency	Does selective context retrieval reduce token consumption, costs, or development time without reducing correctness?
RQ4: Scalability	Does the usefulness of the proposed framework change as the codebase grows in size and complexity?
These are separate questions because your framework might improve one dimension while making another worse.

For example, persistent memory might increase correctness but also add 15% to token costs. That would be an important trade-off, rather than an unqualified improvement.
3. Exactly what would you compare?
You need at least three different development environments, all working on the same programming tasks.
A

Baseline: Normal repository

A standard application with source code, a README, tests, and normal developer tooling. No specialized AI instructions.

The agent can explore files and run tests independently.



B

Existing approach: AGENTS.md

The same repository, but with a carefully written AGENTS.md providing architectural information, commands, and project-specific instructions.

This represents an approach developers already use.



C

Your approach: SADE

The same application with your structured knowledge layer, task handovers, context retrieval, and architectural validation.

This is the experimental treatment.



You then measure whether C produces better outcomes than A and B.

Why compare against B? Because if you only outperform an agent with no project instructions, you haven't demonstrated that your new framework adds value beyond existing best practices.

A 2026 study by Gloaguen and colleagues found that repository context files did not generally improve task success and increased inference costs by more than 20%. That's a strong reason to test your assumptions experimentally.

4. A complete example of your first experiment
Imagine you're developing an enterprise application that processes customer orders.

It has authentication, orders, payments, inventory, and reporting modules.

You establish one architectural rule:
All payment operations must pass through the PaymentService. The Orders module must not directly modify payment records.

Now you ask the AI to implement a new feature.

Task: "Add order cancellation with an automatic refund for eligible orders."

The agent needs to understand that cancellation requires changing an order's status, validating refund eligibility, calling PaymentService, and preserving the system's audit trail.

You run the same experiment three times under each environment, starting from the same repository commit and using isolated sessions.
Illustrative results — hypothetical, not real data
Metric	A	B	C
Tests passed	14/20	16/20	19/20
Architecture violations	3	2	0
Tokens consumed	85k	92k	70k
Completed correctly?	No	No	Yes
These numbers merely show what an experiment might measure. Three runs per condition would be a pilot, not enough for strong general conclusions.
If results like these repeat across many independent tasks, they could support the claim that your structure helps AI respect architectural boundaries and implement features correctly.

But you need to consider alternative explanations. Perhaps C succeeds merely because you gave it more information. Perhaps it succeeds because its validator catches an error that A and B are not checked for.

Therefore, your experiments must distinguish between the benefits of information, its organization, its retrieval mechanism, and its enforcement.

All versions should have the same underlying application tests and objective quality checks. Whether the agent can see particular context or validation feedback is a separately controlled experimental factor.
5. How do you test persistent memory?
This is especially interesting because it directly addresses your concern about AI forgetting previous work.
Experiment: Continue a feature after a session reset
Session 1
Initial work

The agent begins implementing multi-tenant authentication. It makes architectural decisions, changes several files, and identifies outstanding work.
Clear conversation history; retain repository changes

Agent without structured memory

Starts a fresh session with the modified repository and original task description.


Agent with structured memory

Starts a fresh session with the same modified repository and task description, plus the saved architectural decisions and task handover.




Compare outcomes

Does the agent correctly resume the feature? Does it preserve previous decisions? How much exploration and rework does it need?


For example, the previous session decided that every database query must enforce tenant isolation.

Without a handover, an agent might fail to discover this requirement. With a structured handover, it should have a better opportunity to find and respect that decision.

You can measure:
- Percentage of tasks completed correctly after the reset.
- Number of previously established constraints violated.
- Number of unnecessary changes to previously completed code.
- Tokens, tool calls, and time needed to resume.
- Frequency of missing, stale, or incorrect information in saved memory.
You should also compare structured memory against a simple plain-text handover. Otherwise, you might prove that giving an agent a handover helps, but not that your particular structure is necessary.
6. How do you test whether your design scales?
There are two different definitions of scalability here, and you should keep them separate.

Application scalability concerns whether software handles increasing users, requests, and data volumes.

AI development scalability concerns whether coding agents remain effective as repositories grow in size, dependencies, modules, and historical decisions.

Your proposed research primarily investigates the second.

This is potentially the most challenging of your research questions because building realistic comparison repositories takes substantial effort.
7. How many experiments would you need?
I would separate your research into a small pilot study and a larger evaluation.
Stage	Design	Purpose
Pilot	5 tasks × 3 conditions × 3 runs = 45 runs	Check that the tests and experiments actually work
Main evaluation	20 tasks × 3 conditions × 5 runs = 300 runs	Estimate differences with more reliable evidence
Component analysis	Disable one framework feature at a time	Determine which components contribute to improvements
External validation	Repeat selected experiments on another repository or AI model	Check whether results generalize
These are suggested study sizes, not statistically justified minimums. You would refine them after the pilot based on observed variation, costs, and desired precision.

An important research technique here is an ablation study.

Suppose your complete framework improves task correctness. Which component actually caused the improvement?

You compare:
- Full framework
- Framework without persistent memory
- Framework without selective context retrieval
- Framework without architectural instructions
- Framework without additional agent-facing validation feedback
That helps determine whether individual components have measurable benefits, and whether they interact.

You should also run the experiments with:
1. The same pinned AI model and agent version.
2. Identical repository starting commits.
3. Equivalent task instructions and execution budgets.
4. Fresh, isolated working environments for each run.
5. Automated hidden tests and predefined scoring rules.
6. Recorded token counts, tool calls, costs, and failures.
One major risk is information leakage: you must not accidentally put the hidden test solutions or reference patches into your framework's context files.

10. What would I actually do first?
I would not immediately attempt the full four-question research program. That's too much to validate before you know whether the idea has merit.

I recommend starting with one narrowly defined study:
Does structured persistent project knowledge improve an AI coding agent's ability to complete interrupted software engineering tasks compared with ordinary repository instructions and simple handover notes?

Why start here? Because you can build a working experiment relatively quickly, measure an identifiable failure mode, and create the foundation for the larger framework.

Your first implementation would only need:
- One moderately complex repository, ideally an application with several interdependent modules.
- Five carefully designed interrupted-development tasks.
- Three initial conditions: no handover, simple handover, and your structured handover.
- A script that runs each task in two independent agent sessions.
- A test suite and experiment logger that records correctness, architectural violations, tokens, and costs.
After this first experiment, you could investigate selective retrieval, architecture enforcement, and larger repositories independently.
The central distinction
Your engineering project is the framework you create.

Your research project is the evidence showing whether, when, and why it works.

Your portfolio demonstration is the real application built using that framework, together with its measured results.

I would prioritize producing a defensible, reproducible experiment over making the framework elaborate. If your first experiment shows that a structured handover provides no advantage over a simple Markdown file, that is useful evidence: you would know not to overengineer that part of the system.

The strongest outcome is not necessarily proving every initial idea correct. It is developing an architecture whose complexity is justified by measured improvements.
