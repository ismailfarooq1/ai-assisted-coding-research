# Prospective measured A/B study

This study compares A (Memos's existing workflow and native documentation) with B (a new, metered preparation of additional project context plus the native workflow). C remains an undecided shell. The earlier pilot, its repeated task, original context pack and measurements remain historical and are not pooled into this study.

## Questions and sampling

Does additional prepared context improve independently verified task completion under common execution limits? What incremental preparation, execution and maintenance resources accompany the observed outcomes?

Six researcher-selected, small frontend utility tasks, each in a different source file, receive two fresh attempts per method: 24 coding runs. This is an exploratory convenience sample within one revision of one application, not a representative sample of Memos development or company work. Tasks are specified before new context preparation, and hidden acceptance checks are unavailable to preparation/coding actors. The preparation actor receives native documentation/configuration, not task descriptions or solutions. A new pack is created because historical preparation cost was not recorded; its cost cannot be assigned retrospectively to the old B runs.

Task pairs are balanced: A first once and B first once within each task. A fixed seed orders the 12 task/attempt blocks before coding. All coding attempts run sequentially from clean copies, without human repair. Both methods use the same pinned image, model, reasoning setting, limits and task prompt except B's instruction to read its additional context. Fresh CLI homes retain local session usage only inside each private container; only usage metadata is extracted, not authentication or private transcripts. No other method's changes, logs or evaluation are exposed. Network access allows the provider; external solutions are prohibited by prompt but shell egress is not technically restricted to provider domains.

## Completion and evaluation

The primary outcome is verified completion for each attempt, requiring: successful agent exit without timeout; permitted source/test edits and unchanged HEAD; at least one changed or added test; hidden acceptance checks; independently passing candidate-written/changed test files; native lint; pristine upstream regression tests; and production build. Failed runs remain in denominators. No best-of retry, manual code repair or replacement task is allowed. Missing evaluation due to an infrastructure fault is unresolved, never silently passed or discarded. Resume may finish missing independent evaluation; it may not replay an already-started coding attempt. Skipped or focused test registrations and removal of upstream assertions are flagged for human adjudication before any final quality claim. Test success is a limited behavioral measure, not proof of maintainability/security or all possible correctness.

Every hidden evaluator must reject the unmodified baseline and accept a researcher-written positive control before agents run. Positive controls validate the evaluator and are never mounted in agent containers. Baseline lint, native tests and build must pass. Evaluation uses fresh offline containers with no credentials; candidate tests are graded before pristine tests are restored for the separate regression check. All stages and exit statuses are retained. Independent evaluation overhead is measured separately from coding-method effort.

## Resource boundary

Report each stage separately: automated context preparation and any repair attempts; actual human context review; each coding attempt including failures; automated context maintenance; actual human maintenance review; independent evaluation. Report shared environment/harness work separately when observed. Coordinator conversation tokens and prior harness engineering time are unavailable; they are outside this incremental method-cost comparison, not zero.

- Tokens: recorded input, cached-input subset, output and reasoning-output subset. Total = input + output. Never add cached/reasoning subsets twice. Cross-check completed-turn CLI events with fresh-session cumulative token-count metadata; failed/interrupted turns may still have unreported usage and are explicitly marked incomplete. No hard token cap is enforced by this CLI; wall-clock limit is 600 seconds per coding/preparation/maintenance stage, 2 CPUs, 4 GB, 256 PIDs. Independent evaluation limit is 900 seconds. Stop before further coding if authentication/rate-limit/provider infrastructure fails; preserve started attempts and resume only unstarted ones after recovery.
- Time: Docker-invocation-to-exit wall time, plus inner command wall time; evaluation and preparation separate. Summed sequential run time is not a forecast of organizational delivery time.
- Local compute: cgroup CPU seconds (local container descendants); sampled maximum memory.current every 100 ms, including cache/kernel. No inference-server CPU, energy or exact peak RSS claim.
- Human effort: server-recorded participant-controlled active intervals with start, pause, resume and completion; automatic pause after missing heartbeat or hidden tab. These intervals measure observed review participation, not verified attention. No response/waiting interval is counted as human labor. Save actual judgments and edits with before/after hashes. Do not reconstruct labor from agent duration.
- Money: actual per-run billed amounts are unavailable with current account login. Do not turn API list prices into observed subscription spending. Any later monetary scenario must state its supplied rates and assumptions separately.

A's pre-existing documentation investment is historical and unobserved. A has no *additional* context-generation stage within this incremental adoption boundary; that does not mean native guidance is costless. B prep is amortized explicitly over observed tasks/attempts and hypothetical reuse counts only as a labeled scenario. Report total resources across all attempts and resources per verified completion, undefined when there are no successes. Show input/cache/output components rather than treating equal total tokens as equal expense.

## Human review and maintenance

The user has agreed to timed human review. Before coding, review the new B pack against its cited source excerpts, recording each claim as supported, corrected, unsupported or unresolved and coverage of routing, verification, toolchain, generated-file rules and authority. Corrections are captured within timed intervals. Unsupported/unresolved claims must be corrected or removed; do not approve a pack automatically. This is required study data, not another permission request. The local review server never starts coding itself.

Two prospective controlled change episodes follow coding, each independently derived from the original snapshot: (1) rename the frontend lint script to check and update CI invocations; (2) rename the Vitest config to vitest.project.config.mts and update test/watch/coverage scripts to reference it. Apply the same source/config change to both isolated methods; existing context is carried forward only within its own method. Maintenance actors update native guidance for A and native plus additional context for B. These are designed documentation stress cases, not a frequency estimate for natural project changes. Human review order is A/B in episode 1 and B/A in episode 2. Same-reviewer carry-over remains a limitation. Record stale assertions, corrected/remaining assertions, common required facts covered, unresolved judgments, edit scope, automated resources and observed human intervals. A changed source hash is only a review trigger; it is not itself a stale factual claim.

## Analysis and decision boundaries

The independent unit is the task (six clusters); the two attempts within a task estimate repeat variability. Report per-task completion fractions, paired A/B differences and all 24 outcomes. An exploratory two-sided exact paired sign-flip test uses six task-level differences (all 64 label swaps); alpha=0.05 for this single primary contrast, no secondary significance fishing. Only interpret that test under its within-pair label-exchangeability assumption; fixed-seed order balancing does not create a representative population sample. With six tasks, inference is coarse and power low. Report the attainable p-value and effect, not a claim of equivalence after a null result. Do not treat 24 attempts as 24 independent tasks.

Secondary comparisons describe paired token/time/CPU differences over all attempts, sampled memory, reliability of completed checks, preparation and two maintenance episodes. Report failures and missing costs. No unchosen quality/resource weights are hidden in a composite score. A workflow is empirically preferable on a stated criterion only within the tested scope; if completion is similar but resource dimensions conflict, report the trade-off. Whole-workflow savings or company superiority require evidence beyond this exploratory study. No numerical savings or general winner is presupposed.
